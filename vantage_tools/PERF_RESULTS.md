## UI-freeze finding (the important caveat)

- the dashboard's `gather` is invoked synchronously on the Qt main thread (vantage_addon/__init__.py `reload()`), so its p95 of 149 ms (load) / 138 ms (refresh) is a main-thread block above the 100 ms no-freeze rule. It stays inside the explicit load/refresh budgets, so this is a wiring fix (run it off-thread), not a scoring-cost failure.

## Top optimization opportunities

1. Run `gather` off the UI thread (aqt QueryOp / taskman.run_in_background) and show a spinner: the dashboard then never blocks the main thread at any deck size. It is currently called synchronously in vantage_addon/__init__.py `reload()`. (Biggest win: fixes the freeze rule.)
2. Memoize `outline.match_tag` per distinct tag string: this deck has only 18 distinct tags but `gather` calls match_tag once per card, so the tag->concept loop drops from 6.04 ms to 4.97 ms (~1.07 ms saved) at this size. Safe, pure-Python, no behavior change.
3. The per-card retrievability scan (`_cards_r_and_tags`) is 89.0 ms and grows linearly with deck size; if the dashboard ever needs to be synchronous, aggregate tag->concept coverage in SQL (GROUP BY tags) to avoid marshalling 50000 rows into Python.

## Mapping to PRD §11

- **Button press acknowledged (< 50 ms):** `col.sched.answer_card` — the grade write on Again/Hard/Good/Easy.
- **Next card after grading (< 100 ms):** `col.sched.get_queued_cards` on the interleaved queue.
- **Dashboard first load (< 1 s):** cold `anki.vantage.collect.gather(col)`.
- **Dashboard refresh (< 500 ms):** warm `gather(col)`.
- **Any UI freeze never > 100 ms:** worst-case of the interactive actions above; the cold queue build and dashboard load are cold-start costs judged against their own budgets.

## Honest notes

- All explicit p50/p95 latency budgets are met.
- Caveat: the §11 "never freeze > 100 ms" rule is NOT met by the dashboard as currently wired — `gather` runs synchronously on the Qt main thread, so the ~250 ms call blocks the UI. It is within the explicit load/refresh budgets; the fix is opportunity #1 (run it off-thread). The per-keystroke review actions (button ack, next card) are sub-millisecond and never freeze.

- The dashboard number is the cost of `gather(col)` exactly as the task defines it (default args). It is dominated by two full-table SQL passes (the per-card retrievability scan and the reasoning-outcome revlog join) plus a Python `match_tag` per card, so it grows ~linearly with deck size. Parsing the AAMC outline JSON is NOT a factor (measured ~0.06 ms) — see the attribution table above for where the time actually goes.
- The review loop grades cards the real interleaved queue serves (mostly the intraday-learning backlog a fresh build leaves due); costs are not sensitive to which of the four grades is used.

### Build robustness finding (100k)

The first 100k build **crashed** the Rust backend with `attempt to add with overflow` at `rslib/src/decks/stats.rs:32` (`c.milliseconds_studied += input.millisecond_delta`). Cause: every synthetic review is answered within a single collection-day, so the deck's per-day `milliseconds_studied` counter (an i32, reset only on a day change) accumulated all ~400k reviews' answer times and overran 2^31 near ~94k cards. This is a benchmark-build artifact (real spaced use spreads reviews across days and resets the counter daily), not a steady-state user bug. The harness now uses `_simulate_reviews_bounded` (small per-review answer time) so the counter stays well under the limit; the measured actions are unaffected. It is, separately, a real overflow edge in the core deck-stats code worth an `i64`/saturating add upstream.
