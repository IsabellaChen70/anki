## Sync (5th PRD action)

Pre-registered target (fixed before running, honesty-first): PRD §11 "sync of a normal session < 5 s on a normal connection" (docs/prd-vantage.md ~line 322). Measured as the p95 of an incremental ("normal") `col.sync_collection(auth, sync_media=False)` against a real self-hosted Anki sync server (`python -m anki.syncserver`), each after grading one card so there is a genuine one-card delta to push — the same Rust sync path desktop and AnkiDroid use.

- deck used for sync: **2000 cards** (8166 revlog rows) — deliberately smaller than the 50k deck used for every other action, because a 50k full upload is slow. All rows above except the sync row are the 50k numbers; only the `sync (incremental)` row uses this 2000-card deck.
- endpoint: `http://127.0.0.1:8080/` (self-hosted, loopback)
- incremental sync p50 / p95 / worst over 20 one-card syncs: **2.16 / 2.58 / 2.65 ms** (target p95 < 5000 ms -> **PASS**)
- initial full upload (seeds the server; a cold-start cost, NOT judged against the 5 s incremental budget): 51.0 ms
- honesty caveat: the server runs on loopback (same machine), so this measures the sync protocol + client/server processing cost, NOT wide-area network latency. A real broadband connection adds round-trip time (a normal sync does a few round trips), but for a one-card delta that stays far under the 5 s budget. What this proves: Vantage's per-session sync payload and processing are negligible; the only real risk against the 5 s budget is the user's own connection, not the app.

## UI-freeze finding (the important caveat)

- No UI-freeze concern at any deck size: the dashboard's gather + render run off the Qt main thread via `QueryOp(...).run_in_background()` (`vantage_addon/__init__.py` `reload()`), and only the webview swap returns to the main thread. The gather cost is therefore judged only against the load(<1s)/refresh(<500ms) budgets, never the 100 ms no-freeze rule.

## Top optimization opportunities

The two biggest wins are already shipped — `gather` runs off the UI thread (QueryOp, so no freeze at any size) and the reasoning-outcome revlog query is short-circuited in the read path. What remains:

1. Memoize `outline.match_tag` per distinct tag string: this deck has only 18 distinct tags but `gather` calls match_tag once per card, so the tag->concept loop drops from 5.59 ms to 4.48 ms (~1.11 ms saved) at this size. Safe, pure-Python, no behavior change.
2. The per-card retrievability scan (`_cards_r_and_tags`) is 88.0 ms and grows linearly with deck size; if the dashboard ever needs to be synchronous, aggregate tag->concept coverage in SQL (GROUP BY tags) to avoid marshalling 50000 rows into Python.

## Mapping to PRD §11

- **Button press acknowledged (< 50 ms):** `col.sched.answer_card` — the grade write on Again/Hard/Good/Easy.
- **Next card after grading (< 100 ms):** `col.sched.get_queued_cards` on the interleaved queue.
- **Dashboard first load (< 1 s):** cold `anki.vantage.collect.gather(col)`.
- **Dashboard refresh (< 500 ms):** warm `gather(col)`.
- **Sync of a normal session (< 5 s):** incremental `col.sync_collection(auth, sync_media=False)` (one-card delta) against a self-hosted sync server — see the Sync section above for the deck size.
- **Any UI freeze never > 100 ms:** worst-case of the interactive actions above; the cold queue build and dashboard load are cold-start costs judged against their own budgets.

## Honest notes

- All explicit p50/p95 latency budgets are met.
- The dashboard never freezes the UI: `gather` + render run off the Qt main thread via `QueryOp(...).run_in_background()` (`reload()`); only the webview swap is on the main thread. The gather cost is an O(cards) background computation judged against the load(<1s)/refresh(<500ms) budgets. The per-keystroke review actions (button ack, next card) are sub-millisecond.
- Read-path efficiency: the reasoning-outcome revlog query is short-circuited in `collect._merged_outcomes` (skipped via `_has_reasoning_cards` when the collection has zero application items), so early-usage collections don't pay the full revlog join + tag LIKE scan shown in the attribution table.

- The dashboard number is the cost of `gather(col)` exactly as the task defines it (default args). It is dominated by two full-table SQL passes (the per-card retrievability scan and the reasoning-outcome revlog join) plus a Python `match_tag` per card, so it grows ~linearly with deck size. Parsing the AAMC outline JSON is NOT a factor (measured ~0.06 ms) — see the attribution table above for where the time actually goes.
- The review loop grades cards the real interleaved queue serves (mostly the intraday-learning backlog a fresh build leaves due); costs are not sensitive to which of the four grades is used.

### Build robustness finding (100k)

The first 100k build **crashed** the Rust backend with `attempt to add with overflow` at `rslib/src/decks/stats.rs:32` (`c.milliseconds_studied += input.millisecond_delta`). Cause: every synthetic review is answered within a single collection-day, so the deck's per-day `milliseconds_studied` counter (an i32, reset only on a day change) accumulated all ~400k reviews' answer times and overran 2^31 near ~94k cards. This is a benchmark-build artifact (real spaced use spreads reviews across days and resets the counter daily), not a steady-state user bug. The harness now uses `_simulate_reviews_bounded` (small per-review answer time) so the counter stays well under the limit; the measured actions are unaffected. It is, separately, a real overflow edge in the core deck-stats code worth an `i64`/saturating add upstream.
